Mais do que mais agentes

Muitas ferramentas deixam você rodar vários agentes lado a lado. O Pyloxa cuida do que acontece entre eles: quem faz cada parte, como você sabe que terminou e quem assume quando um trava.

Aqui está o mesmo pedido de três jeitos: alternando entre CLIs por conta própria, colocando vários terminais de agentes lado a lado num multiplexador de terminal e entregando ao Pyloxa.

Dividir o trabalho Você decide qual ferramenta serve para cada parte e cola o pedido nela. Você decide o que o agente de cada terminal faz; algumas ferramentas também deixam um agente iniciar agentes auxiliares. O cérebro divide o pedido em fases e tarefas e roteia cada uma pelas suas regras, indicando a regra aplicada.
Passagem de trabalho Quando um agente termina, você cola o formato da API e os caminhos dos arquivos no próximo. Os agentes podem trocar mensagens; o que é repassado fica a critério deles. A próxima fase recebe um pacote de passagem: os resultados, as verificações que passaram e os pontos de atenção.
Concluído significa O agente diz que terminou, e você roda os testes para saber. Você vê quais agentes estão trabalhando, concluídos ou esperando por você; conferir se o resultado está certo continua com você. Uma tarefa está concluída quando seus comandos de verificação passam no worktree dela. Se falharem, o agente ganha uma correção automática. Você também pode pedir que outro agente escreva os testes e que o cérebro revise; o veredito do cérebro vem marcado como revisão de IA.
Sem cota Você troca de ferramenta e explica de novo em que pé as coisas estão. Aquele terminal para e espera; organizar quem assume fica com você. O Pyloxa propõe o fallback das suas regras; depois que você confirma, o trabalho continua a partir dos arquivos que o primeiro agente alterou.
Seu repositório O agente edita seu diretório de trabalho diretamente. Depende de como você abre o terminal; geralmente é seu diretório de trabalho. Cada tarefa trabalha no próprio git worktree, e as alterações são conferidas contra o escopo de escrita permitido. Mesclar e fazer push continua sendo decisão sua.
Ideal para Uma coisa de cada vez. Acompanhar muitos terminais ao mesmo tempo, manter agentes rodando mesmo depois de fechar o app ou trabalhar em máquinas remotas. Dividir um pedido entre agentes e conferir os resultados antes de mesclar.

Divida o trabalho do seu jeito

Quais modelos usar, qual trabalho vai para quem e quando o Pyloxa deve parar e perguntar: tudo isso são configurações suas. O cérebro só propõe planos; ele não pode mudar nenhuma delas.

Cada agente é um perfil que você configura

Um perfil define a CLI, o modelo, o nível de raciocínio e um prompt de papel adicionado a toda tarefa. Uma CLI pode ter vários, como “Claude frontend” e “Claude docs”.

  • A lista de modelos vem direto da CLI que você instalou. O nível de raciocínio usa os valores próprios de cada CLI (o --effort do Claude Code, o model_reasoning_effort do Codex) em vez de uma escala comum inventada.
  • Qualquer perfil pode ser o cérebro que lê o projeto e escreve o plano, e o cérebro pode usar um modelo diferente dos agentes que fazem o trabalho.
  • Perfis guardam só configurações, nunca credenciais.

Suas regras decidem quem faz o quê

As regras combinam tipo de fase e tipo de tarefa, por exemplo “trabalho de backend na fase de implementação vai para Codex backend”. Cada regra tem um perfil principal e uma ordem de fallback, e vale para todos os projetos ou só para o atual.

  • As regras são verificadas de cima para baixo, e a primeira que combina por completo vence. O Pyloxa avisa quando uma regra esconde outra.
  • A simulação de regras não chama nenhum agente nem gasta cota: escolha um tipo de tarefa e veja quem a recebe e por quê.
  • Quando nada combina, o Pyloxa pergunta na prévia do plano ou para, como você preferir. Ele nunca escolhe um agente ao acaso.

Cada fase é conferida com seus comandos

O cérebro monta as fases de acordo com o pedido, como especificação, contrato, implementação e testes. Antes de aprovar, você pode reatribuir uma tarefa, editar as instruções dela ou pedir que o cérebro revise.

  • Comandos de verificação como npm run test precisam da sua aprovação, e você pode testá-los antes num worktree temporário. O cérebro só pode usar comandos que você aprovou.
  • Cada tarefa concluída é conferida no próprio worktree; no fim de cada fase, o gate roda de novo sobre o resultado integrado.
  • Um gate pode seguir sozinho quando passa ou esperar sua aprovação.
  • Entregue uma tarefa concluída a outro agente para testá-la, por exemplo: o Codex implementa e o Claude Code escreve os testes. Quem testa só pode alterar arquivos de teste, e o Pyloxa roda seus comandos de novo sobre o resultado.
  • O cérebro pode revisar o trabalho concluído, com modelo e esforço de raciocínio próprios. O veredito dele vem marcado como revisão de IA, e uma tarefa que pede sua revisão continua esperando por você.

Você decide quanto delegar

O modo de roteamento decide quando o Pyloxa pergunta antes. Em qualquer modo, push e deploy nunca acontecem sozinhos.

  • O cérebro e os agentes de trabalho são configurados separadamente; um agente de trabalho sem cota nunca substitui o cérebro.
  • Cada tarefa tem no máximo 3 tentativas automáticas, e os planos têm limites de tarefas e de tempo, então nada fica tentando para sempre.

Quando um esgota

Se o Codex atingir o limite de uso no meio de uma tarefa, o Pyloxa para de enviar trabalho para ele, mostra quando a cota renova e oferece o fallback da sua regra. Você confirma, e o Claude Code continua a partir dos arquivos que o Codex já alterou.

3 tentativas automáticas por tarefa No máximo 2 fallbacks 0 cobranças de API que você não autorizou

Rode meus testes em toda tarefa.

O npm run test roda no worktree de cada tarefa. Se passar, a tarefa é aceita para você; se falhar, o agente ganha uma correção automática.

Pergunte antes da próxima fase.

Uma fase passa nos seus comandos sobre a versão integrada e depois espera um clique seu. Deixe desligado e as fases conferidas seguem sozinhas.

Nunca toque nas minhas credenciais.

O Pyloxa só roda as CLIs em que você fez login. Ele nunca lê, copia ou envia os tokens delas, e seu diretório de trabalho nunca passa por stash nem reset.
