攻略

AI Agent 說做完了，你要怎麼確認？

合併 Claude Code 或 Codex 的成果之前，一套實際可行的驗收方法：自己跑檢查、看 diff，再請第二個 Agent 依規格審查或補測試。

更新於 2026 年 11 月 19 日

簡短回答

把 Agent 回報的「做完了，測試全過」當成一句說法，不是結果。在 Agent 的分支上，由你自己或 CI 跑專案原本的測試、lint、建置命令；整份 diff 都要看，尤其是測試檔的改動；再核對改到的檔案有沒有超出這個工作允許的範圍。想要第二意見，就把規格（而不是第一個 Agent 的推理過程）交給另一個 Agent，最好是別家廠商的模型，請它審查或補測試，但不要讓它自己動手改程式碼。

為什麼 Agent 說「做完了」不算證據

寫程式的 Agent 覺得看起來完成了，就會停下來。Anthropic 自己的 Claude Code 最佳實務文件就寫得很直白：如果 Agent 手上沒有可以執行、能告訴它到底做完沒的檢查，它就只能憑「看起來做完了」判斷；光說一句「all tests pass」，能告訴你的資訊很少。這對任何 Agent 都一樣。常見的出錯方式：

  • 測試根本沒跑，或只跑了一個檔案，或是跑在舊的建置、不同的環境上。
  • 測試被改了：斷言被放寬、失敗的案例被刪掉，或測試被標成 skip、only。
  • 測錯東西：新加的測試驗證的是程式現在的行為，不是需求要的行為。
  • 範圍跑掉：改到工作範圍以外的檔案，包括 CI 設定、測試設定，甚至 Agent 自己的指示檔。

這些都不需要什麼惡意。只要寫程式、決定檢查什麼、回報結果的是同一個流程，就會發生。解法是把檢查移到 Agent 管不到的地方。

自己跑專案原本的檢查

真正能下定論的，是你的測試在 Agent 的分支上跑過，而且是由你或 CI 啟動、輸出就在你眼前。用團隊平常用的命令，不要用 Agent 為這個工作臨時挑的。

git fetch origin
git switch agent/task-42
npm ci
npm test
npm run lint
npm run build
  • 重新安裝相依套件，避免測到 Agent Session 留下來的東西。
  • 跑完整的測試，不是只跑 Agent 提到的那幾個。
  • 如果要 Agent 自己檢查，就要它拿出證據：實際執行的命令和輸出。
  • Claude Code 也可以強制檢查：Stop hook 會在 Claude 要結束回合時執行你的腳本，腳本以代碼 2 結束時，Claude 就得回去繼續做。

看 diff，先從測試看起

讀實作之前，先看改了什麼、改在哪裡，再拿檔案清單和工作允許的範圍比對。

git diff --stat main...agent/task-42
git diff --name-only main...agent/task-42
git diff main...agent/task-42 -- '*test*' '*spec*'
diff 改到要確認
既有的測試檔除非工作本來就要求，否則沒有斷言被放寬或刪除，也沒有測試被跳過
測試或建置設定測試路徑、覆蓋率門檻、lint 規則沒有被放寬
CI workflow沒有步驟被拿掉，或被改成一定會通過
CLAUDE.md、AGENTS.md 這類 Agent 指示檔這個改動真的是你希望之後每個 Session 都遵守的
工作範圍以外的檔案每一個都有你認同的理由

可以順手搜尋新加的 skip，例如 git diff main...agent/task-42 | grep -nE '^\+.*(\.skip\(|\.only\(|pytest\.mark\.skip)'，再依你的測試框架調整。

每個工作用自己的分支或 worktree

一個工作一個分支，上面每項檢查都會簡單很多：diff 只有這個工作，重跑測試也不會混到別的改動。git worktree 是一份獨立的 checkout，有自己的分支，兩個 Agent 可以同時工作，不會改到同一個資料夾。

git worktree add -b agent/task-42 ../myapp-task-42 main
cd ../myapp-task-42
# 在這裡跑 Agent，再跑你的檢查
git worktree remove ../myapp-task-42

Claude Code 內建這個功能：claude --worktree task-42 會在自己的 worktree 開一個隔離的 Session。repo 至少要先有一個 commit。

怎麼讓第二個 AI 審查或測試程式碼

第二個 Agent 只有在不會順著第一個講的時候才有用，所以要把它安排成沒辦法順著講。

  1. 給它規格，不要給第一個 Agent 的推理交出工作描述或規格檔，加上 diff。第一個 Agent 的摘要不要給，讓審查者判斷成果本身，而不是它對成果的說法。
  2. 請它對照規格檢查例如：「對照 SPEC.md 審查 main 與這個分支之間的 diff，確認每項需求都有實作、列出的邊界情況都有測試。只回報影響正確性的缺口，風格問題跳過。不要修改檔案。」記得叫它跳過風格：被要求找問題的審查者，一定找得到東西。
  3. 或請它寫測試讓它依規格補測試，只能動測試檔，然後由你自己跑命令。事後用 git diff --name-only 確認它只改了測試檔，也不要讓原本的 Agent 去改它補的測試。
  4. 用別家廠商的模型讓 Codex 審 Claude Code 的分支，或反過來。不同模型不是從同一套假設出發，看法比較獨立，但一樣可能看錯。
  5. 別讓審查者偷偷修發現的問題交回給寫程式的 Agent，再重跑檢查。審查者一動手改，就變成第二個作者，而它的改動沒有人審。

兩家都有內建的審查命令。它們都是 AI 審查，不是跑測試。

工具命令做什麼
Claude Code/code-review（別名 /review）審查目前分支的改動，或你指定的 PR、分支、路徑、commit 範圍，找正確性 bug；在一個沒看過你對話的 subagent 裡執行。只回報，加上 --fix 才會套用修正。
Claude Code/security-review檢查你的分支與 origin 預設分支之間的 diff 有沒有安全問題。
Codex CLI/review審查未 commit 的改動、某個 commit 或與基準分支的差異，也可以給自訂指示；回報依優先順序排列的問題，不會修改你的工作目錄。
Codex CLIcodex review --base main同樣的審查，非互動模式，對照基準分支。也可以改用 --uncommitted、--commit 或自訂指示（擇一）。
# 讓 Codex 審查 Claude Code 寫的分支
git switch agent/task-42
codex review --base main

# 讓 Claude Code 審查 Codex 寫的分支，不修改檔案
claude -p "/code-review main...agent/task-43"

審查和其他 Session 一樣會用到你訂閱方案的額度或 API 費用。審查沒找到問題，不代表可以不跑測試。

可以直接複製的檢查清單

- [ ] 這個工作在自己的分支或 worktree 上完成
- [ ] 我自己（或 CI）在這個分支上跑過安裝、測試、lint、建置
- [ ] 我看的是命令輸出，不是 Agent 的摘要
- [ ] 改到的檔案符合工作允許的範圍
- [ ] 既有測試沒有在沒理由的情況下被放寬、刪除或跳過
- [ ] CI、測試設定、Agent 指示檔沒有我沒要求的改動
- [ ] 第二個 Agent（盡量是別家廠商）已對照規格審查
- [ ] 審查者只回報；作者修正；檢查重跑過
- [ ] 合併與否由我決定

Pyloxa 能幫上什麼

Pyloxa 是一個免費的 Windows 應用程式，讓 Claude Code 和 Codex CLI 在同一個專案裡一起工作，上面這份清單大部分它會替你做。Agent 說做完了不算數：工作完成後，Pyloxa 會在那個工作自己的 worktree 裡執行你核准過的驗證命令（測試、建置、lint），並檢查改動的檔案有沒有超出計畫允許的寫入範圍。只有至少有一項檢查、全部通過、而且不需要人工審查時，成果才會自動接受；檢查沒過，會請同一個 Agent 修正，每個工作最多自動執行三次。

  • 交叉測試：由另一個 Agent（例如 Codex 測 Claude Code 的成果）補測試，Pyloxa 自己重跑你的命令，以命令的結果為準。測試者只能改測試檔，補上的測試原本的 Agent 改不掉。免費版按「交給另一個 Agent 測試」；Pro 依設定自動進行，測試沒過會自動交回修正。
  • 大腦驗收（免費）：大腦只讀不改地檢查完成的工作，它的判斷會標示為 AI 判斷。大腦不會驗收自己做的工作。
  • 改到 .github、CLAUDE.md、AGENTS.md、.mcp.json 或定義驗證命令的檔案時，一律不自動接受。合併、推送、開 PR 都等你按下。
  • 驗證報告卡（免費）可以附在 PR 上：每份成果由誰完成、誰交叉測試、Pyloxa 跑了哪些命令、怎麼被接受的。最後一行可選擇加上，只有每個成果都通過 Pyloxa 執行的命令、每個 Gate 也都通過時，才會寫「Verified with Pyloxa」，否則寫「Verification record by Pyloxa」。

如果你只用一個 Agent 做小改動、每次都自己看，或是 CI 本來就會跑每個 Agent 分支、你也會看 diff，那就不一定需要它。設定精靈裡免費的試駕，會用一個藏了 bug 的範例專案走一遍完整流程，不會碰到你的專案。詳細說明：工作流程：檢查、說明：驗證、大腦驗收與交叉測試。

常見問題

為什麼 Agent 說測試都過了，我跑卻失敗？
通常是它只跑了一部分、在後來又改了程式之前跑的、環境不一樣，或是憑記憶回報。請它給出實際的命令和輸出，再自己在乾淨安裝的環境跑完整測試。
可以讓同一個 Agent 審查自己寫的程式嗎？
效果不如換一個新的審查者。Claude Code 的 /code-review 在沒看過你對話的 subagent 裡執行，這樣比較好；換成別家廠商的模型、依規格審查，又更獨立。不管哪一種，下定論的是測試結果，不是審查意見。
可以讓審查者直接修它找到的問題嗎？
可以，但那些修改也要有人檢查。Codex 的 /review 只回報、不改你的工作目錄；Claude Code 的 /code-review 要加 --fix 才會改。把修正留給原作者、再重跑檢查，比較好追。
怎麼防止 Agent 為了過測試去改測試？
在工作說明裡講清楚，然後實際擋住：每個分支都看測試檔的 diff；在 Claude Code 可以用 PreToolUse hook 擋下對指定路徑的修改。由另一個 Agent 寫測試也有幫助。
AI 程式碼審查過了就可以合併嗎？
不行。它能抓到測試抓不到的問題，但終究是判斷。合併的依據應該是你跑過、有通過的命令，你看過的 diff，以及你自己對驗證、金流、資料庫遷移這類高風險部分的審查。
